# PRレビュー

PRを読み、レビューに必要な情報を `tasks/reviews/{リポジトリ名}-pr-{番号}/` に保存する。GitLabのMRでは `tasks/reviews/{リポジトリ名}-mr-{番号}/` とする。本スキルの「PR」はGitLabのMRも指す。

パスは、作業を始めたGitリポジトリのルート（以下、ワークスペース）からの相対パスで書く。ワークスペースは、レビュー対象のリポジトリそのものでも、対象を `repo/{リポジトリ名}` に置いた別のリポジトリでもよい。プロジェクトが別の保存先を決めていれば、それに従う。

作業ディレクトリは未追跡のファイルとして作られる。対象リポジトリのコミットに含めない。必要なら `.gitignore` に足すか、`--out-dir` でリポジトリの外に出す。

この文書のコマンドの `{owner}/{repo}` には、collect_pr.py が出力した対象の値を書く。`gh api` は `{owner}` と `{repo}` をそのまま渡すと、カレントディレクトリのリポジトリの値に置き換えるので、対象を別の場所に置いているときに別のリポジトリを操作してしまう。

作業の範囲は資料の作成までとする。PRへのコメント投稿、Approve、マージ、コードの修正は、指示があるまで行わない。

投稿を指示されたときは、次のように扱う。

- 「Draftでコメントして」は、GitHubのPendingのレビュー（`gh api -X POST repos/{owner}/{repo}/pulls/{番号}/reviews` に `event` を付けない）として作り、Submitしない。`commit_id` には、レビューしたheadのSHAを渡す。コメントは、PRの差分に含まれる行にインラインで付ける。対象の行が差分にないときは、その行を使う差分の箇所（呼び出し元など）に付ける。
- GitLabでは、使える手段（GitLabのMCP、`glab`）で公開前の下書きにできるかを確かめる。できなければ投稿せず、利用者に伝える。
- 投稿の前に、PRのheadがレビューしたcommitと同じかを確かめる。違えば、投稿せずに利用者に伝える。
- Approveやレビューの送信の本文は、利用者が指定した文言をそのまま使う。

## 前提

- GitHubのPRには `gh`（認証済み）を使う。
- GitLabのMRには、対象リポジトリのチェックアウトと `git` を使う。本文、パイプライン、コメント、承認の取得には、GitLabのMCPか `glab` のどちらかが要る。
- `python3`（標準ライブラリだけを使う）。

## 手順

### 1. PRの事実を集める

このスキルのディレクトリにある `scripts/collect_pr.py` を、ワークスペースのルートで実行する。

```bash
python3 {このスキルのディレクトリ}/scripts/collect_pr.py <番号|PRやMRのURL> [--repo {対象}] [--forge github|gitlab] [--out-dir tasks/reviews] [--target-branch {ブランチ}] [--base {SHA}]
```

- URLを渡せば、対象のリポジトリはURLから決まる。GitLabのMRは手元のチェックアウトから読むので、チェックアウトがワークスペース自身でも `repo/{リポジトリ名}` でもないときは、`--repo` にそのパスも渡す。
- 番号だけを渡すと、現在のリポジトリのoriginを対象にする。別のリポジトリなら、`--repo` にチェックアウトのパス、`repo/` 配下のディレクトリ名、GitHubの `owner/name` のいずれかを渡す。
- GitHubかGitLabかは、URLの形か、originのホスト名で判断する。番号だけを渡したときは、ホスト名に `github` を含まなければGitLabとして扱う。ホスト名に `github` を含まないGitHub Enterpriseでは `--forge github` を渡す。
- 出力のタイトルが依頼と食い違うときは、リポジトリを利用者に確かめる。

スクリプトは作業ディレクトリを作り、規模、マイグレーションの信号、テストの変更を出力する。GitHubではCI、既存のレビューの件数と状態、PR本文も出力する。信号は候補であり、信号がないことは「不要」の根拠にならない。開いているPRのマージ可否が `UNKNOWN` のときは、GitHubの計算待ちなので、`gh pr view {番号} -R {owner}/{repo} --json mergeable,mergeStateStatus` で取り直す。

GitLabのMRでは、スクリプトがMRのコードを `git fetch` し、手元の差分から集計する。次のものは、スクリプトを実行する前に、GitLabのMCPか `glab` で取得する。

- タイトル、本文、状態、マージ先、競合の有無。
- 規模（スクリプトの集計との照合に使う）。
- パイプラインの結果と、失敗したジョブ。
- 既存のレビュー（ディスカッション、承認）。

`glab mr view {番号} --comments` は、端末以外から実行すると、パイプライン、承認、競合の有無を出力しない。足りない項目は、`glab mr view` のJSON出力（`-F json`）か、`glab api` でGitLabのAPIを読んで補う。取得する手段がないときは、取得できなかった情報を報告に書く。

スクリプトには、次のように渡す。

- マージ先がデフォルトブランチでなければ、`--target-branch` に渡す。
- マージ済みでheadがマージ先に含まれるMRは差分を求められないので、スクリプトの案内に従って `--base` を渡す。
- マージやクローズから時間がたったMRは、`refs/merge-requests/{番号}/head` が消えていて取得できない。その場合は、ソースブランチかマージコミットから読む。

次のものも読む。

- 作業ディレクトリの既存の文書と、保存先のディレクトリにある `AGENTS.md` / `CLAUDE.md`。
- 対象リポジトリの `AGENTS.md` / `CLAUDE.md`、レビューの手引き、変更領域の設計文書。
- 関連Issue（GitHubは `gh issue view`）。
- 既存のレビューの本文と会話コメント（GitHubは `gh pr view {番号} -R {owner}/{repo} --comments`）、インラインコメント（GitHubは `gh api repos/{owner}/{repo}/pulls/{番号}/comments --paginate`）。collect_pr.py は本文を取得しない。既存の指摘は、修正が正しいかだけを確かめ、指摘を重ねない。
- アーキテクチャ知識グラフ（memory MCPの `search_nodes`）があれば、変更するモジュールと依存関係。グラフにないことを、依存がない根拠にしない。

`review.md` が既にあれば再レビューとする。前回のheadは `review.md` の「対象」から読む。手順2でコードを取得した後に、前回のheadとの差分（`git diff {前回のhead}..{今のhead}`）を読み、`review.md` の末尾に「## 修正の確認（日付）」を追記する。force pushで前回のheadを取得できないときは、全体を読み直す。書式は `references/review-template.md` に従う。

### 2. PRのコードを手元に用意する

利用者のチェックアウトでは、ブランチを切り替えない。作業中の変更を壊さないためである。

```bash
git -C {チェックアウト} fetch origin pull/{番号}/head                 # GitHub
git -C {チェックアウト} fetch origin refs/merge-requests/{番号}/head  # GitLab（collect_pr.py が取得済み）
git -C {チェックアウト} show {headのSHA}:{パス}
```

一式が必要なら、`git -C {チェックアウト} archive {headのSHA} | tar -x -C {一時ディレクトリ}` で展開する。チェックアウトがないリポジトリは、一時ディレクトリへcloneする。隣接リポジトリを参照するときは、参照したコミットを `review.md` に書く。ローカルのHEADは古い場合があるので、先に `git fetch` する。

### 3. 読み方を決める

collect_pr.py の「進め方の推奨」に従う。規模が基準未満でも、独立した領域が3つ以上あるなら分ける。基準以上でも、生成コードやロックファイルが大半なら、それを除いて判断する。

- **1人で読む場合** — 差分の全体を読み、呼び出し元までたどる。
- **分ける場合** — `references/reviewer-brief.md` に従い、領域ごとにレビューエージェントを並列に起動する。指示文にPRの背景を書くので、手順4の背景を先にまとめてから起動する。待つ間にシーケンス図を書き、指摘を受け取ったら手順5で検証する。サブエージェントを使えない環境では、領域ごとに順に読む。

### 4. 背景と対応前後の流れを把握する

コードを評価する前に、次の問いに答える。

- なぜこの対応が必要なのか。どの症状や要望から始まったのか。
- この対応は何を解決するのか。解決しないものは何か。
- 不具合の修正なら、不具合はどの機構で起きるのか。PR本文の説明をコードで確かめる。

PR本文とIssueとコードのどこにも根拠がなければ、推測で補わず「背景は未記載」と書き、指摘の一覧に観点を「背景」として載せる。

シーケンス図は、変更の前後で何が変わったかを比べるために書く。

- Mermaidの `sequenceDiagram` を前後で1つずつ書く。登場人物の名前を前後で揃える。
- 簡易的に保つ。登場人物は6以下、矢印は15本以下を目安とし、変更と関係しない経路は省く。
- 図の前に1文で、その図の要点を書く。
- 処理の流れが変わらない変更（文書のみ、リファクタリングなど）は図を省き、変わらないと判断した根拠を書く。

### 5. 6つの観点を確認し、指摘を検証する

`references/perspectives.md` を読み、デグレード、セキュリティ、パフォーマンス、スケーラビリティ、マイグレーション、テストをすべて確認する。問題がない観点も、確認した範囲と根拠を書く。マイグレーションでは `references/migration-surfaces.md` も読む。

指摘を文書に書く前に、次のことを確かめる。

- 重要度が高と中の指摘は、エージェントの報告であっても、コードを直接読んで確かめる。確かめられない指摘は「未確認」と明記するか、削る。
- 指摘は、PRが原因か、PR以前からあるかを区別する。
- PRのheadで確かめる。baseが進んでいるなら、baseにも残るかを確かめる。
- 実行していない検証を、実行したように書かない。

### 6. 成果物を書く

`references/review-template.md` の構成で、作業ディレクトリに次の3つを保存する。

- `README.md` — PRの要約と、各文書への案内。
- `review.md` — レビュー結果の本体。
- `comment-draft.md` — PRに付けるコメント案。書き方は `references/comment-style.md` に従う。対象は重要度が高と中の指摘とし、なければ作らない。

文書は次の規則で書く。プロジェクトに文章の規範があれば、それにも従う。

- 確かめたことと推論を分けて書く。確かめたことには、読んだファイルと行、実行したコマンド、見たログを添える。
- ファイル名、関数名、ジョブ名、コミット、HTTPステータスなどの識別子は、実名で書く。
- 誰が、または何が（どのサービス、どのジョブ、どのブランチ）その動作をするのかを省かない。
- 確かめた範囲をそのまま書く。一部のテストだけを実行して「全件成功」と書かない。

### 7. 報告する

次のことを短く報告する。

- 結論と、重要度が高と中の指摘。
- マージ前後に必要な作業。
- 確認できなかったこと。
- 作成した文書のパス。
- 調査で見つけた、文書とコードの食い違い。

### 8. 依頼元への返信を作る

複数のPRのレビューを終えて、依頼元へ返す文面を頼まれたら、PRごとの結果を1行ずつ並べる。利用者がそのまま貼れるように、コードブロックで示す。

```text
レビューしました。指摘数は以下の通りです。

{PRのURL} : 1件
{PRのURL} : OK
```

- PRは、依頼されたときの順に並べる。
- 結果は、PRに投稿した指摘の数（「1件」）か、指摘なしでApproveしたPRの「OK」とする。数えるのは実際に投稿したコメントで、`review.md` の低の指摘など投稿しなかったものは数えない。
- 冒頭と末尾の文言は、利用者やチームの決まりがあればそれを使う。
