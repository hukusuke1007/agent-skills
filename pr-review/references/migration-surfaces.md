# 反映経路の一覧

コードをマージしても反映されないものを探すための一覧である。ここに書くのは、どのプロジェクトにも当てはまる起点だけである。実際の経路は、対象のbaseブランチのCIの定義とデプロイの設定で確かめる。

## 確かめる順序

1. PRのマージ先のブランチが、どの環境に対応するかを確かめる。マージ先と、本番に届く時期は別のことがある。
2. CIの定義（`.github/workflows/`、`.gitlab-ci.yml` など）を読み、変更したパスがどのジョブを起動するかを確かめる。パス条件に当たらない変更は、デプロイされない。
3. 下の表で、変更の対象ごとの反映の経路を確かめる。
4. マージで自動的に反映されないものは、`perspectives.md` の5点（誰が、いつ、どの手順で、どう確かめ、どう戻すか）がPRに書かれているかを確かめる。

## 変更の対象ごとの起点

| 変更の対象 | よくある反映の経路 | 確認すること |
| --- | --- | --- |
| DBのマイグレーションファイル | デプロイのパイプラインの中の1ステージ、または手動のコマンド。 | アプリのデプロイとの順序。旧版のアプリと互換か。ロールバックの手段。 |
| テナントごとのDBやスキーマ | マイグレーションの仕組みの対象外で、全テナントへ手動で流すことがある。 | 適用状態が記録されるか。途中で失敗したときの再開の手順。検証のSQL。 |
| データ移行やバックフィルのスクリプト | 手動で実行する。 | 実施の時期、対象、再実行の安全性、途中失敗からの再開。 |
| APIスキーマ（GraphQL、OpenAPI、protobuf） | サーバーとクライアントのデプロイに時間差がある。 | 削除と変更の差分。利用箇所の削除と定義の削除を、別のリリースに分けているか。 |
| データストアのルール、インデックス | デプロイのジョブ、または手動のコマンド。 | インデックスの作成完了を待つ必要があるか。ルールの変更が既存のクライアントを拒否しないか。 |
| 環境変数、Secret | アプリのリポジトリでは完結せず、インフラのリポジトリやホスティングの設定に要ることが多い。 | 全環境に値があるか。反映済みか。マージと順序が合うか。読む側に権限があるか。 |
| 新しいクラウドリソースへのアクセス | 実行ロールやサービスアカウントへの権限付与が、インフラの側に要る。 | PRと別に権限の変更が要るか。本文に手順と順序があるか。 |
| CIの変数（`vars.*`、`secrets.*`） | リポジトリやグループの設定を手動で変更する。 | 全環境の値が設定済みか。 |
| Terraformなどのインフラの定義 | planはCIで流れても、applyは手動のことがある。 | applyの実施者と時期。import、destroy、再作成の有無。state移行の要否。PRと無関係の既存差分が同時に反映されないか。 |
| コンテナイメージ、ビルドの設定 | ビルドのジョブ。`Dockerfile` の `COPY` の対象が、CIのパス条件にも含まれる必要がある。 | 足したファイルがイメージに入るか。パス条件から漏れていないか。 |
| テナントや組織ごとに配る設定・実行環境 | 順に反映するので、反映まで旧版が動くテナントがある。 | 新旧の互換。対象を限定して反映する手順が要るか。 |
| 取り込んだ成果物（`vendor/`、固定した版やコミット） | 依存先の公開と、利用側の版の更新が別々に要る。隣接ソースの編集だけでは反映されない。 | 依存先が先に公開されているか。lockfileの版。利用側の更新PRが要るか。 |
| 文書だけのリポジトリ | 公開のジョブ。 | 反映の作業はない。設計と実装の食い違いを確かめる。 |

## リポジトリをまたぐ変更

- サービス間の呼び出しの契約が変わるなら、両方のマージの順序と、片方だけが新しい間の動作を確かめる。
- CIのplanやビルドが成功しても、実環境の状態との一致や反映の成功は保証されない。

## プロジェクト固有の一覧

同じプロジェクトを繰り返しレビューするなら、プロジェクトの文書（保存先のディレクトリの `AGENTS.md` など）に、上の表と同じ3列で固有の経路を書いておく。確かめた日を添え、レビューのたびにbaseブランチの定義と照らす。固有の一覧があれば、この一覧より先にそれを読む。
