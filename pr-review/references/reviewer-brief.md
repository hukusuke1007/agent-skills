# レビューエージェントの分け方

## 分割

領域で分ける。認証、APIの入口、アップロード、管理画面のように、機能のまとまりで2〜4体とする。観点で分けない。同じ差分を観点の数だけ読み直すことになり、領域の文脈も失うためである。

マイグレーションの信号があり、別リポジトリ（インフラの定義など）の確認が要るときは、横断担当を1体足す。この担当は、担当領域の代わりに `perspectives.md` のマイグレーションだけを確認する。指示文では、6観点の段落を「{perspectives.md の絶対パス} のマイグレーションの節と {migration-surfaces.md の絶対パス} を読み、マージ以外に要る作業だけを確認してください。」に差し替える。

自分でも全体の差分を確認し、背景、シーケンス図、指摘の統合を担当する。エージェントは読み取り専用で使い、ファイルを保存させない。

汎用のサブエージェントを、並列に起動する。

## 指示文の雛形

エージェントはこの会話の文脈を持たないので、指示文に必要な情報をすべて書く。パスは絶対パスで書く。

```text
{リポジトリ} PR #{番号} の「{領域名}」をレビューしてください。読み取り専用で作業し、ファイルは保存しないでください。

目的: {PRの背景と解決すること。2〜3文}
head: {SHA}（ローカルでは git -C {チェックアウトのパス} show {SHA}:{パス} で読める）
base: {SHA}
担当ファイル: {パスの一覧}
担当外: {ほかのエージェントが見る領域}。担当外の問題に気付いたら、調べずに報告だけしてください。
既知の指摘: {既存のレビューで指摘済みの内容}。重ねて指摘しないでください。

{perspectives.md の絶対パス} を読み、デグレード、セキュリティ、パフォーマンス、スケーラビリティ、マイグレーション、テストの6観点で確認してください。マイグレーションでは {migration-surfaces.md の絶対パス} も読んでください。差分だけでなく、呼び出し元と呼び出し先までたどってください。

次の形式で日本語で報告してください。

1. 指摘: 重要度（高・中・低）、観点、ファイルと行番号、問題が起きる条件と結果、PRが原因かPR以前からか、根拠にしたコード。
2. 問題がなかった観点: 確認した範囲と根拠。
3. 確認できなかったこと。

実際に読んで確かめたことだけを書いてください。推測は推測と明記してください。
```

## 結果の統合

- 重要度が高と中の指摘は、自分でコードを読んで確かめる。
- 複数のエージェントの指摘の重複をまとめ、重要度の基準を揃える。
- 領域の間にまたがる問題（領域Aの変更と領域Bの前提の食い違い）を確認する。
- `review.md` の「対象」に、分けた領域と、直接確かめた指摘を書く。
