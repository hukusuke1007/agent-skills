# レビューの6観点

各観点の項目は確認の起点である。PRと関係しない項目は省き、確認した範囲と根拠を書く。

## デグレード

- 既存の動作や契約の変化。API、イベント、ジョブ、保存データの形式、既定値。
- 呼び出し元への影響。変更した関数やスキーマの利用者を、リポジトリの外（別サービス、公開パッケージ）までたどる。
- エラー時と境界条件の振る舞い。空、上限、同時実行、再送、タイムアウト、部分失敗。
- 新旧の混在。デプロイの途中やテナントごとの反映待ちの間に、旧版と新版が同時に動いても壊れないか。フロントエンドは、利用者がリロードするまで旧版が動き続ける。実行中のジョブやセッションも、終わるまで旧版で動く。
- 既存テストで守られていない経路。

## セキュリティ

- 認証と認可。入口ごとの本人確認、テナントの境界、権限の再確認。認可がクライアント側ではなくサーバー側で担保されているか。
- 秘密情報（鍵、トークン）の渡し先と露出範囲。ログ、エラー文言、子プロセス、クライアントへの応答。
- 入力検証。SSRF、オープンリダイレクト、インジェクション、パストラバーサル、サイズの上限。
- 権限の広がり。IAM、ストレージやデータストアのアクセスルール、CORS、公開範囲。

## パフォーマンス

今の利用量のままで、変更した経路が遅くならないか、資源を余分に使わないかを見る。量が増えたときの振る舞いは、次のスケーラビリティで見る。

今の量で実害がある指摘はパフォーマンスに、量が増えて初めて問題になる指摘はスケーラビリティに書く。同じ指摘を両方に書かず、片方から参照する。

- 応答時間と処理時間。利用者が待つ経路（画面の表示、APIの応答）と、時間の制限がある経路（ジョブ、Webhook、タイムアウト付きの呼び出し）に、処理が足されていないか。
- 追加の呼び出しとI/Oの回数。ループの中のクエリや外部呼び出し（N+1）、同じデータの読み直し、並列にできる処理の直列の実行。
- クエリの効率。インデックスを使えない条件や並べ替え、不要な列や行の取得、全件の読み込み。
- 計算量とメモリ。入れ子のループ、大きなデータのコピーや一括の展開、ストリームにできる処理の全量の読み込み。
- キャッシュ。無効にする条件、古い値を返す期間。キーにテナントや権限が含まれず他人の値を返す問題は、セキュリティに書く。
- フロントエンド。不要な再描画、バンドルのサイズ、初回表示を止める読み込み。
- 起動時とデプロイ時の処理。コールドスタート、初期化で行う重い処理。

推測で問題にしない。変更の前後で増える呼び出し回数や処理時間の見積もりを添える。測定できるなら測定し、測定していないことは書く。

## スケーラビリティ

入力の量、テナント数、同時実行数が増えたときに何が起きるかを見る。

- 待ち時間とタイムアウト。外部呼び出しの上限、リトライが重なったときの負荷。
- 量に比例して増える呼び出しとI/O。テナントの全データの走査、件数に上限のない一括処理。
- 同時実行が増えたときの直列化、ロック、トランザクションの競合。
- リソースの使用量。メモリ、DBの接続数、インスタンスやタスクの数と同時実行、外部APIのレート制限、コスト。
- データ量の増加。件数が増えるとインデックスが効かなくなる条件、ページング、保存期間。

推測で問題にしない。量の見積もり（1回あたりの呼び出し回数、想定件数）を添える。

## マイグレーション

そのPRのために、コードのマージ以外の作業が要るかを確かめる。

- DBのマイグレーション、データの追加と変換、バックフィル。
- インフラの権限付与（IAM、Secretへのアクセス、APIの有効化）、リソースの作成。
- 環境変数とSecretの追加。全環境（開発、ステージング、本番、プレビューなど）に値が要るか。
- テナントごとの再反映、依存パッケージの公開と取り込み。

必要な作業ごとに、次の5点が明確かを確かめる。

1. 誰が実施するのか。
2. いつ実施するのか。マージ前、マージ後、デプロイ前後の順序。
3. どのコマンドや手順で実施するのか。
4. 実施したことをどう確かめるのか。
5. 失敗したときにどう戻すのか。

順序は、新旧の混在を前提に決める。たとえば、列を削除するPRが旧版の稼働中に反映されると旧版が失敗するので、参照の削除と列の削除を別のリリースに分ける必要がある。

作業が必要なのにPR本文に手順がなければ、指摘にする。本番の障害やデータの損失につながるなら重要度を高とする。

不要と判断したときも、根拠を書く。「マイグレーションのディレクトリとAPIスキーマに差分がない」のように、確かめたコードで示す。

## テスト

- 変更した振る舞いごとに、それを検証するテストがあるか。正常系だけでなく、失敗時、境界条件、権限の拒否。
- 不具合の修正なら、修正前に失敗するテストがあるか。
- テストの構成が本番と同じ経路を通るか。モックの境界が本物の挙動を隠していないか。たとえば本番は複数のワーカーで動くのに、テストのワーカーが1つなら、複数のときの経路は未検証である。
- CIで実際に実行されるか。ワークフローのパス条件、変更の有無による実行条件、手動のジョブで漏れていないか。
- 手動の確認が必要な範囲。PR本文の確認が実環境で行われたものか。

足りないテストは、追加するケースを具体的に書く。テストで確かめられず実環境の確認が要るときは、手順を書く（再現、修正前の測定、反映、修正後の測定）。

変更に関係する小さいテストは、手元で実行できれば実行する。依存の導入が重い場合は実行せず、実行していないことを書く。
